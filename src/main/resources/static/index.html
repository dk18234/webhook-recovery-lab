THE SYSTEM

A PostgreSQL inbox. A fenced worker. An atomic ledger.

A single Spring Boot service keeps the boundaries easy to inspect. PostgreSQL is both the durable inbox and the source of truth for the demo credit balance.

Acceptance transaction

Verify, validate, persist

HMAC-SHA256 authenticates the original request bytes and timestamp. A unique event ID rejects conflicting payloads and counts repeat deliveries. HTTP 202 follows the inbox commit.

Claim transaction

Give one worker ownership

A short row lock with SKIP LOCKED selects ready work. A unique lease token fences later writes, and the attempt record is committed before processing.

Business transaction

Apply one protected effect

The event's ledger insert and the account balance update share a transaction. An event ID can enter the credit ledger only once.

Recovery transaction

Reconcile before retrying

An expired lease with a ledger entry is marked successful. Without an entry, it is retried or dead-lettered when its budget is exhausted.

What this version guarantees

  • Accepted work is stored before acknowledgement.
  • Each event ID contributes at most one credit effect inside this PostgreSQL database.
  • Unfinished claims are recoverable after the lease expires.
  • Retry attempts and manual replays preserve the audit history.

Boundaries that matter

There is no claim of exactly-once network delivery. External side effects need their own idempotency or an outbox protocol. Worker pause is per instance. Authentication uses a shared operator token; this is a single-tenant learning project, not a multi-tenant payments product. Failure injection can be disabled.

The hosted browser simulation uses local storage and a simulated clock. The downloadable Java service uses PostgreSQL transactions and is verified by integration tests.

START WITH ONE REQUEST

Reverse-engineer a working system.

  1. Trace acceptance.

    Follow LabController.receive → Signatures.verify → Inbox.accept. Explain why 202 happens after the commit.

  2. Find the duplicate boundary.

    Run duplicate delivery. Locate the event primary key and the unique credit ledger entry. Explain what would break if either constraint disappeared.

  3. Watch a transaction fail.

    Run “Crash before commit.” Check the ledger while the lease is active. Explain why the account update rolls back too.

  4. Recover a committed effect.

    Run “Crash after commit.” Credits exist before completion is acknowledged. Explain how lease recovery uses the ledger as evidence.

  5. Own an extension.

    Add a second synthetic event type, design its business constraint, and prove it remains safe under concurrent duplicate delivery.
